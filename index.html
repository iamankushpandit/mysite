Device · firmware · since Aug 2026

Braino! — a 40-game learning console on a Cheap Yellow Display

▶ Watch the demo

Braino is firmware for the ESP32 touchscreen boards that sell for about fifteen dollars. Flash it and the board becomes a handheld console with forty games for young players: tracing letters and cursive, counting, telling the time, flags, states, chess, Ludo, backgammon, Go, sea battle and more. Up to five player profiles with their own scores and an administrator PIN that gates the settings.

Everything is baked into the 3 MB app partition. There is no SD card, no account and no data collection. Wi-Fi is used for the clock and a daily update-availability check that says nothing about the device. Bluetooth LE is off by default; switched on, two consoles in the same room can play chess, Ludo, backgammon or sea battle against each other over a non-connectable beacon, and the device shows you the exact bytes it transmits.

What is in it

  • 40 games in 82% of a 3 MB flash partition, with no heap allocation anywhere in the firmware.
  • Flash from the browser over Web Serial, including every past release, so there is always a way back from a bad build.
  • Five boards from one source tree: two 2.8-inch CYD variants, a 3.2-inch, a 4-inch ST7796 and the ESP32-S3 Freenove FNK0104B, each described in one profile header.
  • Nine themes, every pairing checked against WCAG contrast floors, with generated mock-ups of every screen in every theme.
  • Synthesised audio. Every cue and the spoken boot phrase are generated from oscillator and formant scripts; there is not one audio file in the tree.
  • A serial console that configures a bench of boards from one JSON file, behind the same PIN as the screens.
  • Printable enclosures per board, and a 3D-printed case line-up pictured above.

Ivy AI — a voice assistant that runs entirely on a $20 microcontroller

Say "Hey Ivy", ask a question, and the board transcribes your speech, runs a language model and answers out loud. No network, no server, no phone. It runs on a Freenove FNK0104B: an ESP32-S3 with 8 MB of PSRAM, a 2.8-inch display, a microphone and a speaker. Wi-Fi exists for one thing only, setting the clock. 

mic → LISTEN (energy VAD) → TRANSCRIBE (conformer CTC)
    → THINK (19.7M-param LLM, 4-bit) → SPEAK (SVOX Pico) → speaker

The interesting problem is memory. The device has 8 MB of PSRAM and about 300 KB of usable internal SRAM, while speech-to-text alone wants 5.4 MB and the LLM 6.5 MB. They coexist by never running at the same time: two arenas are reserved at boot and each phase takes the whole thing, then gives it back. Speed comes from 4-bit weights with int8 activations, a hand-written ESP32-S3 PIE SIMD kernel, and a matrix-vector worker on the second core.

Measured on the board

LLM, TinyTalk v8 (6.5 MB)load 694 ms, 5.4–5.9 tok/s
LLM, any llama.cpp GGUF ≤ 5.8 MB7.3 tok/s at 6.4M params, 30 tok/s at 260K
Speech to text2.7–4.6 s for 1.4–2.9 s of audio
Whole spoken turnroughly 14–17 s, listen to spoken answer
Accuracy, v899.2% on trained wording, 63.3% on rephrasings, 0% facts wrong
  • Drop any GGUF file on the SD card and it appears on the model page; the docs give the fit rules and the vocabulary-shrinking tools.
  • Plain C answers time, date, timers and identity without the model, and the UI marks which path answered.
  • Nothing ever flashes. The screen is a dirty-row text renderer with no framebuffer, and a host harness measures what percentage of the panel each update repainted.
  • Host-first. The UI, the arenas and both LLM engines build and run on a PC, so most work needs no hardware.

LocalGrid — an offline messaging network that forms and heals itself

Put a few powered access points around an area with no signal, hand everyone a touchscreen handheld, and people can message each other. Nobody configures anything after the first setup. It is designed for the moment the infrastructure everyone relies on is not there.

Three radios, each with a job. Wi-Fi (ESP-NOW) carries normal traffic between access points and each handheld's link. LoRa is a second, much longer link between access points for when Wi-Fi cannot reach. Bluetooth lets a laptop watch the network's health without joining it. Emergency alerts go out over Wi-Fi and LoRa at the same time.

What it does

  • End-to-end encrypted 1:1 messages with X25519, HKDF-SHA256 and ChaCha20-Poly1305. Access points carry them without being able to read them.
  • Groups, broadcasts, emergencies that break through every screen including the lock screen, and push-to-talk with 100 ms frames sealed like text.
  • No master, no server. Every access point holds a full replica of settings, groups, presence, grid time and health. Split the network in half and rejoin it and it reconciles on its own.
  • Bounded by design. Fixed-size tables, no heap allocation per message, and a defined, logged result when anything fills up.
  • Six handheld boards plus an ESP32-C6 alert unit, GPS for time and position, and an admin page served from every access point.

Chaos engineering: tested by breaking it

A chaos-engineering framework randomly kills access points and handhelds, cuts their power and switches their radios off, for hours, unattended, while the handhelds keep messaging. In the 10-hour run of 18 September 2026: 55 faults injected, 55 recovered, none needing a human, with the backbone re-forming in a median of 3.7 seconds. It found three bugs that code review and unit tests never could, including the self-healing promise not being true when every access point went down at once.

Library · graphics data · since Aug 2026

map-n-flag — 195 flags and maps for the ESP32, as plain C++ arrays

Country flags and map silhouettes for 195 countries plus 51 US states and DC, baked into flash as const data. No runtime SVG parsing, no SD card, no external asset loading. It was built for a 320×240 Cheap Yellow Display with 4 MB of flash and no PSRAM, but nothing in it is board-specific. It is the artwork behind Braino's flag, map and state games. 

#include "map_n_flag.h"
const mnf_img_t *flag = mnf_flag("FR");   // 80x60 indexed image
const mnf_img_t *map  = mnf_map("FR");    // silhouette, same ISO code
const char      *name = mnf_name("FR");   // "France"
  • Zero RAM. .bss and .data are both 0 bytes, verified with the toolchain's size tool.
  • 1.09 MiB of flash for all 195 flags and 191 outlines; 280 KiB more for the US states, opt-in.
  • One header, thirteen functions, two structs. Lookup is a binary search over a sorted table, safe to call before any display is set up.
  • No LVGL required. Draw rows straight into TFT_eSPI or LovyanGFX as RGB565; LVGL v8 and v9 support is an optional header.
  • Flags and outlines share the ISO key, so a "which flag matches this outline?" game is two calls with one string.

Investigation · 2020

Eclipse SWT drag-and-drop crash — found, reproduced, confirmed, fixed upstream

While upgrading a product from Eclipse 4.7 to 4.16, dragging a string from an SWT application into a WPF application began crashing the Java side, intermittently but often. This repository is the minimal reproduction: an SWT window with a drag source, a C# window with a drop target, and the same code built against SWT 4.12 and 4.13 so the regression is isolated to one library version.

The cause was a change to DragSource in SWT 4.13 that aggressively released every COM object once the drop completed. A drop target that keeps a reference for later use then touches freed memory. The Eclipse Foundation confirmed the analysis on Bug 567422, changed SWT to trust the target to release what it still holds, and shipped the fix in Eclipse 4.18.

  • Side-by-side projects for SWT 4.12, 4.13 and 4.16, plus the compiled C# target, so anyone can reproduce it in minutes.
  • A video and a thread dump of the crash, and the exact SWT source jars compared.
  • Outcome: an upstream fix in the Eclipse platform, credited by the SWT maintainers.

The thread that runs through them

Cheap hardware, finished software

Four of the five run on ESP32 boards that cost between ten and twenty dollars. The constraint is the point: 4 MB of flash and no PSRAM is enough for forty games if nothing is wasted, and a $20 board is enough for a language model if the memory is planned rather than hoped for.

Complete without a connection

None of these devices needs the Internet to do its job. Braino collects nothing and says so on the device. Ivy's radio is off except to set the clock. LocalGrid exists precisely for when the network is gone.

Measured, then claimed

Tokens per second, flash bytes, frame times, recovery seconds: each README states a number and where it came from. LocalGrid's self-healing claim went through chaos engineering, fifty-five faults injected over ten hours while the handhelds kept messaging, and the write-up includes what the test still cannot find.

They feed each other

map-n-flag is the artwork inside Braino. LocalGrid and Braino share five display boards, so a profile written for one ports to the other. Ivy and Braino both run on the Freenove FNK0104B. The Eclipse investigation is the oldest and the odd one out, but it set the pattern: reproduce it, measure it, write it down, send it upstream.
